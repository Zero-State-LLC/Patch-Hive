# Intent

## Problem

Spec 008 research R1: `pin_readiness_docs` and the `operator_pin` guard trusted `verify_enablement_receipt`, an unkeyed SHA check a forged receipt passes, and `pinned_by` was free text. 007 T081 added Ed25519 approver signatures; the pin did not use them.

## Proposed outcome

Pinning requires the 007 receipt's approver signature (`signed_enablement_receipt_failures`). The pin is signed by the approver key under its own signing domain, so `pinned_by` is an allowlisted key id; the pin records `pinned_at`, the 007 signature and its own signature. The `operator_pin` guard and `beta_eligible` verify both signatures.

Out of scope: generating the key (007 T082), signing a real receipt (007 T083), and the operator pin itself (008 T072).

## Affected users / systems

`core/ops/f5_cutover.py`, `intelligence/receipt_signing.py` (a `domain` parameter, default unchanged), 008 tests and operator notes. No runtime route or deployed behaviour.

## Constraints / non-goals

Fail closed on every signature failure. Receipt-signature behaviour is unchanged (same default domain). The private key is only used on the operator's machine; nothing stores it.

None for this task.
