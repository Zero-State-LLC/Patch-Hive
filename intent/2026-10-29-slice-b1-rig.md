# Intent

## Problem

Three gaps in rig intelligence (spec 001, research R2, R3, R4):

- `allow_feedback` and `prefer_simple` are accepted by the API and stored in the IR, but the engine ignores them.
- The generation IR hash covers only rack id, seed, `max_patches` and `allow_feedback`. A changed inventory or engine version leaves it unchanged.
- The rig page shows "Confirm inventory modules" for every empty run, even when validation failed and the cause is a blocking finding.

## Proposed outcome

- `allow_feedback=false` (the default) drops patches that carry a `FEEDBACK_LOOP` finding. The count goes in provenance as `feedback_dropped_count`.
- `prefer_simple=true` stable-sorts patches by cable count before the `max_patches` cut.
- `get_canonical_hash` hashes the IR's canonical JSON, minus run id, timestamp, commit and host, into 32 characters. No migration.
- The rig page branches on `generation_status`: blocking findings for `VALIDATION_FAILED`, the inventory hint for `NOT_COMPUTABLE`, "No patch rule fits this rack." for zero patches.
- Tasks T032, T033 and T034 are ticked. T030 and T031 stay open.

Out of scope: the canon compiler (T030), rig metrics (T031), a `patch_engine_version` bump.

## Affected users / systems

Patch generate (engine, validation, IR), the rig detail page.

## Constraints / non-goals

- No audio DSP, no hardware control.
- No new product behavior beyond the spec.
- No migration. Stored `generation_ir_hash` values keep their old value; new runs get the new one.

## Open questions

- Should the feedback drop happen before the `max_patches` cut, so the cut refills? Today it runs after validation, so a run can return fewer than `max_patches`. The owner decides.
- Should `patch_engine_version` change? Defaults now drop looped patches. No golden output in the tests changed.
