# Intent

## Problem

The 2026-10-27 gap analysis found P1 security gaps that remained after the P0 fixes (#82):

- `canonical_exports.idempotency_key` was unique across all users, so one user reusing another user's key got that user's export back.
- Ops could grant the Admin role.
- Sign-in had no throttling. An unknown username was cheaper to check than a wrong password, which leaked whether accounts exist.
- Password hashing used passlib, which is unmaintained and broken by bcrypt 4.1 and later (5.0 is installed). New users silently got passlib's pbkdf2 fallback.
- Concurrent first purchases could reward one referral twice.
- Nothing pinned the legacy purchases endpoint, which mints a user-chosen `credits_delta`, off by default.

## Proposed outcome

- Export idempotency is unique per `(user_id, idempotency_key)`. Lookups, ids and the debit key are scoped to the user.
- Only an Admin may grant or remove Admin, and role names are validated.
- Sign-in:
  - Every failure answers the same 401 after comparable work.
  - Five failures lock an account for 15 minutes, counted atomically in the database.
  - One address may make 20 attempts a minute.
- New password hashes are Argon2id (pwdlib). Existing bcrypt and passlib-pbkdf2 hashes still verify and are rehashed on the next sign-in.
- At most one `Rewarded` referral per referred user (row lock plus a partial unique index).
- A test pins the legacy purchases endpoint to 404 by default.

Out of scope:

- Moving tokens out of localStorage, short-lived access plus a refresh cookie, and CSP.
- Registration responses that reveal whether a username or email is taken.
- An edge-wide Cloudflare rate-limit rule.
- The acceptance suite's `STAGING_DATABASE_URL` fallback.

## Affected users / systems

- Auth: `/api/community/auth/login`, `users` table.
- Admin role changes: `/api/admin/users/{id}/role`.
- Canonical exports and the credit ledger.
- Legacy referrals.
- Migration `20261028_p1_security`.
- Every existing user: their password hash is upgraded on their next sign-in.

## Constraints / non-goals

- Fail closed. Payments stay in test mode.
- No existing password hash may stop verifying.
- A lock must not reveal that an account exists.
- The per-address limit is in-process, which is enough while the API runs as a single container. It is not a substitute for an edge rule if the API scales out.

## Open questions

- **Lock policy:** are 5 failures and 15 minutes right for production? Owner decides. The values are constants in `community/login_guard.py`.
- **Edge rule:** add a Cloudflare rate-limiting rule for `/api/community/auth/login` when production goes live. Operator decides.

## Verified / assumed claims

| Claim | Label | Basis |
|---|---|---|
| passlib cannot hash with the installed bcrypt 5.0, so new hashes fell back to pbkdf2 | `OBSERVED` | `bcrypt.__about__` AttributeError in the seeder; `pip show bcrypt` = 5.0.0 |
| bcrypt and passlib-pbkdf2 hashes still verify and are upgraded on sign-in | `OBSERVED` | `tests/api/test_p1_security.py`, with real hashes generated by passlib and bcrypt |
| One user's export key no longer returns another user's export | `OBSERVED` | `test_one_users_key_never_returns_another_users_export` |
| Concurrent wrong passwords each count toward the lock | `OBSERVED` | atomic `UPDATE … SET failed_login_count = failed_login_count + 1 RETURNING`; test for the lock |
| The migration upgrades, downgrades and upgrades on Postgres 15 | `OBSERVED` | local postgres:15.13 container; acceptance suite on Testcontainers |
| The in-process address limit holds in production | `INFERRED` | true only while `edge/api` runs one container (`getByName("primary")`) |
| A dummy Argon2 check makes unknown-name timing indistinguishable | `INFERRED` | same hasher and parameters; not measured statistically |
