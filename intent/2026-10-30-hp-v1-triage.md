# Intent

## Problem

`overlays/module-catalog-hp-v1.json` holds 221 HP values with no maker citation. The loader still applies them through `UNSOURCED_HP_OVERLAYS`. #153 corrected three of them. The owner chose triage for the other 218 (decision 9, spec 003 T038). A wrong HP misplaces a module in a rack, and today nothing tells a reader which stored HP is uncited.

## Proposed outcome

- `overlays/module-catalog-hp-v3.json` (v2 schema) re-sources the v1 values whose hp-enrichment result cites the maker's own page, but only where a plain GET of that page states the width for that exact product. Each entry quotes the page. Where the page states another width, v3 carries the page value, so a fresh load and a corrected database agree. (A first version trusted the citations after a 10-page spot check; review found Knit Rider and MEMS Mic 1U wrong, so every page is now checked.)
- `provenance/maker-corrections-v3.json` holds reviewed `correct` entries for each disagreement where the maker page shows the stored value is wrong, in every table that holds it. The loader reads it after `maker-corrections-v2`.
- Migration `20261030_catalog_hp_source` adds a nullable `module_catalog.hp_source`. The loader sets it to `legacy_unsourced` when the stored HP equals the uncited v1 value and no maker source carries an HP for the slug. It clears the marker once that changes. The catalog API returns the field.
- T038 is ticked. T039 stays open for the free maker-page lookup of the values v3 does not cover. Then `UNSOURCED_HP_OVERLAYS` can go.
- Out of scope: that lookup, and removing `UNSOURCED_HP_OVERLAYS`.

## Affected users / systems

`module_catalog` and `modules` on staging and prod (eight HP values across four modules, plus the `hp_source` marker on about 88 rows), the catalog loader, the catalog API (`hp_source` field), and alembic (one additive column).

## Constraints / non-goals

Values come only from a maker page. Use free plain GETs only, with robots.txt respected, 2 s apart per host, stopping a host at its first block or CAPTCHA. No ModularGrid. Corrections fire only while the stored value is the reviewed old value. HP stays fill-null. The marker never writes HP. Dry run, then apply with the reviewed `plan_hash`.

## Open questions

- 1U widths: the catalog has no form-factor column, and each Intellijel 1U row stores the HP its maker page states (Xfade 1U 26, Quadratt 1U 28, Buff Mult 1U 14). MEMS Mic 1U is corrected to its stated 10 HP on that basis.

- Does staging's real history differ from the replay for the nine disagreements whose stored value the replay shows as the maker value (from `catalog-additions-v1`)? A read-only query, or the staging dry run, answers this. If a row holds the v1 value, a later manifest corrects it.
- ADDAC200PI: the maker site returned a bot challenge, so 2 (v1) versus 4 (crawl v1) is unresolved. It stays `legacy_unsourced`.
